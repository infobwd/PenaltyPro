### แนวทางที่พิสูจน์แล้วและควรทำซ้ำ

1. **คง `?action=xxx` แบบเดิมของ Apps Script ไว้ทั้งหมด** — sillapa73 ย้าย frontend ด้วยการเปลี่ยน `API_URL` + ใส่ `Authorization` header เท่านั้น
   ⇒ PenaltyPro ทำแบบเดียวกันได้: `sheetService.ts` คง signature เดิม เปลี่ยนแค่ปลายทาง **คอมโพเนนต์ 23 ตัวไม่ต้องแก้**
2. **`row_version` optimistic locking** — ทุกการเขียนตรวจ version ถ้าชนคืน `409` พร้อมค่าปัจจุบัน ไม่เขียนทับเงียบ
   ⇒ ใช้กับ `matches` (บันทึกผลสดหลายคนพร้อมกัน) และ `teams` (โรงเรียนแก้พร้อมแอดมินอนุมัติ)
3. **`legacy_sha256` password migration** — เก็บ `password_algo` ไว้ แล้วอัปเกรดเป็น bcrypt ตอนผู้ใช้ตั้งรหัสใหม่ + `must_change_password`
4. **ตัด PII ก่อนส่ง ไม่ใช่ซ่อนใน UI** — ผู้ไม่ล็อกอินได้ `contact`/`members` เป็นค่าว่างจริง
5. **`getData` ต้องไม่โกหกเวลาระบบล่ม** — ต่อ DB ไม่ได้ต้องตอบ `500` ไม่ใช่ `200` + array ว่าง; response ที่มี warning **ไม่ถูกแคช**
6. **cron ทุก 5 นาที** ผ่าน DirectAdmin หรือยิง URL + `cron_secret`

### 🟢 โรงเรียนหนึ่งส่งได้หลายทีม — ยืนยันจากข้อมูลจริง

`อนุบาลบ่อพลอย A` (สาย D) และ `อนุบาลบ่อพลอย B` (สาย H) คือโรงเรียนเดียวกันส่ง 2 ทีม
**อยู่คนละสายด้วย**

schema จึง **ไม่** ใส่ `UNIQUE (tournament_id, school_id)` แต่คุมเพดานด้วย
`tournaments.max_teams_per_school` ในชั้นแอปแทน (แอดมินปรับได้รายทัวร์นาเมนต์)
ส่วน `UNIQUE (tournament_id, name)` ยังอยู่ — ชื่อทีมห้ามซ้ำ จึงยังกันสมัครซ้ำโดยไม่ตั้งใจได้

**ผลต่อรหัสโรงเรียน:** 1 รหัส = 1 โรงเรียน ⇒ ใส่รหัสแล้วเห็น**ทุกทีม**ของโรงเรียนนั้น
แล้วเลือกแก้ทีละทีม — หน้าโรงเรียนต้องรองรับกรณีมีหลายทีมตั้งแต่ต้น ไม่ใช่สมมติว่ามีทีมเดียว

**ผลต่อแผน:** งานของโรงเรียนไม่ใช่ "ยืนยัน + แก้ไขเล็กน้อย" อย่างที่ประเมินไว้ตอนแรก
แต่คือ **26 โรงเรียนต้องกรอกรายชื่อผู้เล่นใหม่ตั้งแต่ต้น** (ทีมละ ~7 คน + วันเกิด + รูป) ⇒ ต้อง

1. ทำหน้ากรอกรายชื่อให้เร็วที่สุด — กรอกชื่อเรียงลงมาได้ต่อเนื่อง, **รูปเป็นตัวเลือก (ไม่บังคับ)**, บันทึกอัตโนมัติทุกช่อง
2. รองรับกรอกจากมือถือเป็นหลัก (ครูส่วนใหญ่ใช้มือถือ)
3. เผื่อเวลาให้โรงเรียนมากกว่าเดิม — **แจกรหัสให้ทันวันที่ 20 ส.ค. สำคัญขึ้นอีก**
4. แอดมินต้องมีหน้า "ทีมไหนยังไม่กรอกรายชื่อ / กรอกไม่ครบ" เพื่อตามงานได้

## 2. Schema — ส่วนที่เพิ่มจากเอกสารวิเคราะห์

โครงหลัก 21 ตารางยังใช้ตามเอกสารวิเคราะห์หัวข้อ 3.2 **ส่วนต่อไปนี้คือของใหม่ที่เกิดจากความต้องการ 2 ข้อล่าสุด**

### 2.1 แยก "โรงเรียน" (ถาวร) ออกจาก "ทีมที่ลงแข่ง" (ต่อทัวร์นาเมนต์)

นี่คือกุญแจที่ทำให้ดึงทีมเดิมมาใช้ได้ และเป็นสิ่งที่ระบบเดิมไม่มี

```
schools                      ← อัตลักษณ์ถาวร ข้ามทัวร์นาเมนต์
  id, legacy_id, name, short_name, district, province,
  access_code_hash        VARCHAR(255)   ← argon2id ของรหัส 8 ตัว
  access_code_issued_at  DATETIME
  access_code_last_used_at DATETIME NULL
  is_active              TINYINT
  created_at, updated_at

teams                        ← 1 แถว = โรงเรียนหนึ่ง ลงแข่งหนึ่งทัวร์นาเมนต์
  id, legacy_id,
  tournament_id  FK,
  school_id      FK          ← ผูกกลับไปอัตลักษณ์ถาวร
  source_team_id FK NULL     ← ชี้ไปทีมในทัวร์นาเมนต์ก่อนที่ clone มา
  name, short_name, color_primary, color_secondary, logo_url,
  status  ENUM(...)          ← state machine ข้อ 2.2
  group_name VARCHAR(16) NULL,
  reject_reason, doc_url, slip_url,
  director_name, manager_name, manager_phone, coach_name, coach_phone,
  confirmed_at, submitted_at, approved_at, approved_by FK NULL,
  created_at, updated_at
  UNIQUE (tournament_id, school_id)     ← 1 โรงเรียน 1 ทีมต่อทัวร์นาเมนต์
  UNIQUE (tournament_id, name)          ← กันชื่อทีมซ้ำในทัวร์นาเมนต์เดียว
  INDEX  (tournament_id, status), (tournament_id, group_name), (school_id)

players                      ← snapshot ต่อทัวร์นาเมนต์ (ไม่ใช่ master)
  id, legacy_id, team_id FK, tournament_id FK,
  source_player_id FK NULL   ← clone มาจากใคร
  name, shirt_number, position, photo_url, birth_date DATE, created_at
  UNIQUE (team_id, shirt_number)        ← กันเลขเสื้อซ้ำในทีม
```

> **ทำไม `players` เป็น snapshot ไม่ใช่ master:** อายุ/ชั้นเรียน/รายชื่อเปลี่ยนทุกฤดู
> ถ้าใช้ master ร่วมกัน การแก้รายชื่อปีนี้จะไปแก้ประวัติปีที่แล้วด้วย — ผลการแข่งเก่าจะเพี้ยน
> การ clone ตอนสร้างทีมใหม่ให้ทั้งความสะดวก (ไม่ต้องพิมพ์ใหม่) และความถูกต้องของประวัติ

### 2.2 State machine ของทีม

```
        ┌── import ทีมเดิม (แอดมินสั่ง clone จากทัวร์นาเมนต์ก่อน)
        ▼
    Invited ────────────────────────────────► Withdrawn
   (รอยืนยัน)      โรงเรียนกด "ไม่เข้าร่วมปีนี้"
        │ โรงเรียนใส่รหัส เปิดแก้ไข
        ▼
     Draft ──── โรงเรียนกด "ยืนยันและส่ง" ───► Submitted
   (กำลังแก้)                                (รออนุมัติ)
                                                 │
                            ┌── แอดมินอนุมัติ ────┴── แอดมินปฏิเสธ ──┐
                            ▼                                        ▼
                        Approved ◄── แก้ไขได้จนถึง deadline      Rejected
                        (เข้าแข่ง)                            (+ reject_reason)
                            │                                        │
                            └──── แบ่งสาย → group_name ────┘ แก้แล้วส่งใหม่ได้
```

กติกาที่บังคับฝั่ง server:
- โรงเรียนแก้ได้เฉพาะทีมของ `school_id` ตัวเอง และเฉพาะทัวร์นาเมนต์ที่ยังไม่เลย `registration_deadline`
- สถานะ `Approved` แล้วโรงเรียนยังแก้รายชื่อได้ถึง deadline แต่ **ทุกครั้งที่แก้ต้องบันทึก audit log**
- นับ "ทีมที่เข้าแข่ง" ในตัวเลขสาธารณะ = `status = 'Approved'` เท่านั้น (กติกา attribution เดียวของระบบ)

### 2.3 รหัสโรงเรียน + session ของทีม

```
team_sessions
  token_hash   PK
  school_id    FK
  tournament_id FK
  issued_at, expires_at, revoked_at NULL
  ip_hash, user_agent
  INDEX (school_id, expires_at)

access_attempts              ← rate limit / กันเดารหัส
  id, school_id FK NULL, ip_hash VARCHAR(64),
  succeeded TINYINT, attempted_at DATETIME
  INDEX (ip_hash, attempted_at), (school_id, attempted_at)

team_audit_log               ← ใครแก้อะไรเมื่อไหร่
  id, team_id FK, actor_type ENUM('school','admin','system'),
  actor_id VARCHAR(64), action VARCHAR(40),
  field_name VARCHAR(64) NULL, old_value TEXT NULL, new_value TEXT NULL,
  created_at
  INDEX (team_id, created_at)
```

**สเปครหัส:**
- 8 ตัว จากชุด `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (ตัด `0 O 1 I l` ที่อ่านสับสน) → 32⁸ ≈ 1.1 × 10¹²
- เก็บเป็น **argon2id เท่านั้น** — ระบบไม่เก็บรหัสจริง
- แอดมินเห็นรหัสได้ **ตอนสร้าง/ตอนออกใหม่เท่านั้น** (หน้าพิมพ์รายการรหัสทั้งหมดสำหรับแจก)
- ลืมรหัส → แอดมินกด "ออกรหัสใหม่" 1 คลิก (รหัสเก่าใช้ไม่ได้ทันที + เพิกถอน session ที่ค้าง)
- **rate limit:** ผิด 5 ครั้งต่อ IP ใน 15 นาที → หน่วง; ผิด 10 ครั้ง → ล็อก 1 ชม. และแจ้งแอดมิน
- session อายุ 7 วัน, ผูก `tournament_id`, เพิกถอนได้รายตัว

> **ทางเลือกที่ควรพิจารณาในฤดูถัดไป:** ออกรหัสใหม่ทุกฤดูแข่ง (per-tournament code) เพื่อจำกัดความเสียหายถ้ารหัสหลุด
> ฤดูนี้ใช้รหัสระดับโรงเรียนตามที่ตัดสินใจไว้ก่อน เพราะแจกง่ายกว่าและทันเวลา

### 2.4 แบ่งสาย + สร้างตารางแข่ง

```
tournament_groups
  id, tournament_id FK, group_name VARCHAR(16), display_order INT
  UNIQUE (tournament_id, group_name)
```

- แบ่งสาย = `UPDATE teams SET group_name = ?` (แอดมินลากวาง บันทึกเป็นชุดเดียว 1 transaction)
- **ปุ่มสุ่มช่วย:** สุ่มแบบ snake seeding ลงสายที่มีอยู่ + ตัวเลือก "ไม่ให้โรงเรียนอำเภอเดียวกันอยู่สายเดียวกัน" (best-effort) → **ผลการสุ่มเป็นแค่ข้อเสนอ แอดมินต้องกดยืนยันก่อนบันทึก**
- หลังยืนยันสาย: ปุ่ม "สร้างตารางแข่งแบบพบกันหมดในสาย" → สร้างแถวใน `matches` สถานะ `Scheduled` ให้แอดมินใส่วัน/เวลา/สนามภายหลัง
- เก็บ `group_snapshot_at` ไว้กันการแบ่งสายทับหลังเริ่มแข่ง (ถ้ามีนัดที่ `status != 'Scheduled'` แล้ว → เตือนก่อนเปลี่ยนสาย)

## 4. กติกาวิศวกรรมที่บังคับใช้ทุก endpoint

ตาม skill `db-dashboard-builder` — ละเมิดข้อไหนถือว่างานไม่ผ่าน review

1. **PDO placeholder ห้ามซ้ำชื่อในคำสั่งเดียว** (`EMULATE_PREPARES=false` → ซ้ำ = `HY093` แล้วการ์ดว่างเงียบ ๆ) ใช้ `:q_name`, `:q_school` ไม่ใช่ `:q` ซ้ำ
2. **ห้าม `CAST`/`COLLATE`/`LOWER`/`TRIM` บนคอลัมน์ที่ JOIN** — แก้ที่ schema/data ไม่ใช่ที่ query
3. **feed ล่าสุดต้อง LIMIT ก่อน JOIN** (ข่าว/นัดถัดไป/ผลล่าสุด)
4. **ตัวนับที่ผ่าน LEFT JOIN หลายชั้น ใช้ derived table pre-aggregate** ไม่ใช่ `COUNT(*)` ตรง ๆ
5. **ข้อมูลอ่อนไหวกันที่ server** — public ไม่เห็นเบอร์โทร/เลขผู้เสียภาษี/ที่อยู่/ทีมที่ยังไม่อนุมัติ; **cache key ต้องมี flag `admin0/admin1`**
6. **cache key ครบทุกมิติ + bump version ทุกครั้งที่เปลี่ยน shape**
   `penalty_{v}_{section}_{tournament}_{admin0|1}_{page}_{limit}_{qhash}.json`
7. **ทุก query อยู่ใน try/catch ของตัวเอง** เติม `warnings[]` เช่น `Q4_STANDINGS_FAILED` — ห้าม throw ออกจาก endpoint
8. **`?debug=1` คืน `query_timings_ms`** ทุก endpoint ตั้งแต่วันแรก
9. **ทุกการเขียนต้องคืน JSON จริง** — ห้ามใช้ `no-cors` แล้ว `return true` เหมือนระบบเดิม
10. **การแก้ข้อมูลทีมทุกครั้งเขียน `team_audit_log`**

**กติกา attribution เดียวของระบบ:**
> จำนวนทีม/นักเตะ → `teams.tournament_id` + `status='Approved'`
> สถิติผลแข่ง → `matches.tournament_id` และอ้างทีมด้วย `team_a_id/team_b_id` เท่านั้น (**ห้ามจับคู่ด้วยชื่อ**)
> ยอดเงิน → `donations.tournament_id` + `status='Verified'`

```
app_settings ที่เกี่ยวกับ LINE:
  liff_id           ← มีอยู่แล้ว (ใช้ฝั่ง client เรียก liff.init)
  line_channel_id   ← ใหม่ (ใช้ฝั่ง server ตรวจ ID token ว่าออกให้ channel เราจริง)
```

ทั้งสองค่าตั้งได้จากหน้าตั้งค่าแอดมินเหมือนเดิม — ไม่ hardcode
